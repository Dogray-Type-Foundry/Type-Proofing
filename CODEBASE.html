Type Proofing

A macOS app for generating comprehensive PDF proofing documents for fonts. Built with SwiftUI, CoreText, and a Rust native library.

1. What It Does

Type designers need to review their fonts in realistic typographic contexts before shipping. Type Proofing automates this: load one or more font files, pick which proof types you want (character sets, spacing tests, paragraph proofs, Arabic contextual forms, etc.), configure each proof's settings, and generate a multi-page PDF.

Input

Font files (.otf, .ttf) — static or variable.
Per-proof settings (size, columns, OT features, text).
Page format (A4, Letter, Legal, etc.).

Output

A multi-page PDF with:
• Character sets, spacing tests, paragraph proofs
• Arabic/Farsi contextual forms
• Multi-style comparison, GSUB substitution overview
• Headers, footers, baseline grid overlay

The app supports variable fonts with full axis control — weight, width, optical size, slant, and custom axes. For a variable font, the app generates proof pages for every combination of selected axis values (Cartesian product).

2. The Language Layers

Swift
The active app. SwiftUI interface, state management, PDF rendering via CoreText/CoreGraphics. Calls Rust via C FFI for font analysis. This is where all UI and rendering code lives.
Rust
Font analysis engine. Two crates: tp-fonts (charset detection, axis parsing, GSUB extraction, AGL) and tp-bridge (C FFI + WordSiv text generation). Compiled as a universal2 static library.

The app is native-only. There is no Python at runtime — the shipping app is a single native Mach-O binary with no Python.framework. Despite its name, ProofEngine.swift is a native facade over NativeProofOrchestrator.

4. State Architecture

The app uses a hierarchical @MainActor ObservableObject pattern. AppState is the root, with 6 published child objects that are also injected individually into the SwiftUI environment:

TypeProofingApp
  │
  ├── ProofEngine          (Rust FFI wrapper, generation coordinator)
  │
  └── AppState             (root state coordinator)
       ├── FontState       (loaded fonts, axes, styles, sort criteria)
       ├── ProofState      (proof instances, selection, per-proof settings, registry)
       ├── PreviewState    (preview PDF path, sections, fingerprints)
       ├── PageState       (page format, baselines toggle, view mode)
       ├── UIState         (panel visibility, widths, section expansion)
       └── OutputState     (PDF output directory)
Key concept: Proof Instance vs. Proof Type A proof type is a template defined in the registry (e.g., "spacing_proof"). A proof instance is a concrete item in the sidebar with its own UUID, name, and settings. You can have multiple instances of the same type with different settings (e.g., "Spacing Test" with kern on and "Spacing Test 2" with kern off).

Coordinators

Two coordinator objects sit between the state layer and the views:

PreviewCoordinator PreviewCoordinator.swift

Manages live preview generation. Splits proofs into fragments, generates them in parallel, composes them into a single preview PDF. Debounces changes, caches by fingerprint, prioritizes the selected proof.

PDFViewCoordinator PDFViewerView.swift

Manages the PDF viewer. Tracks zoom level, handles section-based navigation, syncs thumbnail sidebar, preserves viewport position across PDF reloads.

5. The Proof System

The proof system has three key concepts:

  1. Registry — A static list of all 22 proof types with their metadata (display name, default settings, capabilities). Lives in ProofRegistry.swift.
  2. Handlers — Classes that implement the ProofHandler protocol to generate PDF pages. Each proof type maps to a handler via NativeProofOrchestrator.makeHandler().
  3. Settings — Per-instance configuration stored in ProofSettings. The registry entry determines which settings controls appear in the UI.

Handler Types

Handler Handles Notes
StandardTextProofHandler 14 text-based proofs Uses TextProofConfig to determine text source, style, language
FilteredCharacterSetHandler Character Overview Category-based, auto-size option
SpacingProofHandler Spacing Test Flanking control characters, force-disables kern
ArCharacterSetHandler Ar Character Overview Shows contextual forms (isolated, initial, medial, final)
CustomTextProofHandler Custom Text User text, markup support, "generate once" mode
SubstitutionOverviewHandler Substitution Overview Reads GSUB table, shows glyph substitution pairs
MultiStyleComparisonHandler Style Comparison Same text across all styles, one line per style

Key rendering components

FontLoader CoreText

Loads fonts from file URLs into the process scope. Creates CTFont instances with OpenType features (via kCTFontOpenTypeFeatureTag), variable axis values (via kCTFontVariationAttribute), and optionally hanging punctuation (AAT feature type 22).

TextRenderer CoreText

Builds NSAttributedString with paragraph styles (alignment, line height, indent, spacing). Two rendering paths: CTFramesetter (default) or NSLayoutManager (when hyphenation is enabled). Handles overflow for multi-page content.

PageLayout Geometry

Computes content rect (margins: 50pt vertical, 40pt horizontal), column rects with configurable gutter, RTL column ordering. Draws the footer with date, font name, proof name, axis label, page number, and OT features summary.

PDFRenderer CGContext

Thin wrapper around CGContext PDF creation. Manages page lifecycle (beginPage/endPage/close), provides drawing primitives (fill rect, stroke line, save/restore state).

8. Live Preview Pipeline

The preview system generates per-proof PDF fragments and composes them into a single preview PDF. This runs continuously in the background as you change settings.

  Settings change (font, proof, toggle, slider...)
         │
         ▼ (debounce 2s)
  ┌──────────────────────┐
  │  invalidateAll() or  │   Marks affected proofs as needing regeneration
  │  invalidateProof()   │
  └──────────┬───────────┘
             │
             ▼
  ┌──────────────────────┐
  │  Queue PreviewJobs   │   Separate queues by cost:
  │  by cost type        │     Fast queue: charset, spacing (parallel, up to N)
  └──────────┬───────────┘     WordSiv queue: text proofs (serial, 1 at a time)
             │
             ▼
  ┌──────────────────────┐
  │  pumpQueues()        │   Dequeues jobs, starts generation tasks
  └──────────┬───────────┘
             │
             ▼
  ┌──────────────────────┐
  │  generateFragment()  │   One PDF per proof, cached by SHA256 fingerprint
  └──────────┬───────────┘   Skips if fingerprint matches existing fragment
             │
             ▼ (debounce 75ms)
  ┌──────────────────────┐
  │  composePreview()    │   Merges all ready fragments into one PDF
  └──────────┬───────────┘   Retains last 2 composed PDFs for smooth transition
             │
             ▼
  ┌──────────────────────┐
  │  Update preview path │   PDFViewerView picks up the new PDF
  │  + sections          │   Viewport position is preserved
  └──────────────────────┘
Why fragments? Generating the entire PDF for every settings tweak would be too slow. By splitting into fragments, only the affected proof is regenerated. Fast proofs (character set, spacing) regenerate in parallel while text-heavy proofs (WordSiv) are serialized to avoid contention.

9. Rust Native Library

The native/ directory contains a Cargo workspace with two crates:

tp-fonts Library

Pure Rust font analysis. Uses read-fonts and skrifa (Google Fonts libraries). Modules: charset (filtered by outline presence), axes (variable font axis values + Cartesian product), substitutions (GSUB single/ligature/contextual lookups), font_info (metadata extraction), agl (Adobe Glyph List fallback).

tp-bridge FFI

C FFI exports wrapping tp-fonts + WordSiv (a text generation library). Outputs a universal2 .a static library via lipo. The C header is auto-generated by cbindgen.

FFI Functions

FunctionPurposeReturns
tp_load_font(data, len) Parse font metadata TPFontInfo* with family, weight, axes JSON, features JSON
tp_get_charset(data, len) Get renderable characters String of characters with actual outlines (not just cmap entries)
tp_get_axes_json(data, len) Variable font axes JSON: [{"tag":"wght","min":100,"default":400,"max":900}]
tp_get_substitutions_json(data, len) GSUB lookup extraction JSON: features with input/output glyph mappings
wsv_text(ptr, glyphs, ...) Generate paragraph text Text using only the provided character set
wsv_words(ptr, glyphs, ...) Generate word list Words matching constraints (case, length, contains)
Memory convention All char * returns from Rust are heap-allocated. The Swift caller must free them via wsv_free_string() or tp_free_font_info(). NULL means error.

Build

bash native/build_rust.sh

# 2. lipo -create → universal2 libtpnative.a
# 3. cbindgen → tpnative.h
# Copy to TypeProofing-SwiftUI/NativeLib/

10. Text Generation

Proof text comes from five sources, chosen by the handler based on the proof's TextProofConfig:

SourceWhen UsedHow It Works
Premade texts When font has full Latin alphabet and proof doesn't force WordSiv Static pangrams and paragraph samples in PremadeTexts.swift
Accented dictionary Diacritic proofs (accents > 0) JSON mapping base characters to words with accented variants
WordSiv When forced, or font lacks full alphabet Rust library generates text constrained to font's charset. Supports English, Arabic, Farsi vocabularies. Seeded (987654) for deterministic output.
Hoefler-style Structured text proofs with hoeflerStyle: true Context-aware word pairing: each character appears next to round, flat, and diagonal neighbors
Custom text Custom Text and Style Comparison proofs User-provided text, optionally with markup (**bold**, *italic*, [text]{attrs}, headings, page/column breaks)

11. Settings & Persistence

Settings auto-save to ~/.type-proofing-swiftui-prefs.json with a 3-second debounce. Users can also export/import settings files for different projects.

Per-Proof Settings

Each proof instance has its own ProofSettings object. The available controls depend on the registry entry's flags:

Registry FlagControls Shown
hasSettingsSettings panel appears at all
hasParagraphsParagraph count slider (1–20)
hasCustomTextText editor + markup toggle + "generate once" + presets
hasCategoriesCategory checkboxes (uppercase, lowercase, numbers, punctuation, accented)
multiStyle (isMultiStyle)Style source picker + font style list + show fallback toggle
supportsCols (derived)Columns (1–6), column gap
supportsFormatting (derived)Alignment, direction, hyphenation, hanging punctuation, paragraph indent/spacing

All proofs also show: font size, line height, tracking, and OpenType feature toggles.

OT Feature Pills

The settings panel shows OpenType features as toggle pills with live preview samples. Features come from the first loaded font's GSUB + GPOS tables. Features in HIDDEN_FEATURES (positional Arabic features, aalt, rand) are never shown. Features in DEFAULT_ON_FEATURES start enabled. The spacing proof force-disables kern.

12. How to Add a New Proof

Adding a new proof type requires changes in 1 to 3 files, depending on whether you need custom rendering:

  1. Register in ProofRegistry.swift
    Add a ProofRegistryInfo entry with key, display name, default size, columns, and capability flags. Add the key to defaultProofOrder. The settings UI renders automatically based on the flags.
  2. If standard text proof: done!
    If your proof just renders text paragraphs, StandardTextProofHandler picks it up automatically via the TextProofConfig. You just need to set the right character set key, paragraph count, and text generation flags.
  3. If custom rendering needed: create a handler
    Implement the ProofHandler protocol, then add a case in NativeProofOrchestrator.makeHandler(). Use the shared utilities (resolveParams, drawContent, FontLoader.makeFont, TextRenderer) for common operations.
No UI code needed The settings panel automatically renders the right controls based on the registry entry's flags (hasSettings, hasParagraphs, hasCustomText, hasCategories, multiStyle). You only need to touch SettingsPanelView.swift if your proof needs a completely novel control type.

13. Gotchas & Non-Obvious Things

Settings key derivation is name-based, not type-based

The flattened settings key for a proof instance comes from its display name (lowercased, non-alphanumeric → underscores), not from the registry key. "Spacing Test 2" becomes spacing_test_2_fontSize, otf_spacing_test_2_kern, etc.

Charset detection filters by outline presence

tp_get_charset() doesn't just read the cmap. It verifies each mapped glyph has actual outlines (contours in glyf, or CFF paths). This filters out empty glyphs, synthesized glyphs, and cmap-only entries. If cmap is empty (rare bitmap fonts), it falls back to the Adobe Glyph List.

Variable font axis values produce a Cartesian product

If a font has wght: [100, 400, 900] and opsz: [8, 32], that's 6 axis combinations. Each combination generates its own set of proof pages. This can multiply page count quickly.

Preview uses fragment composition, not monolithic generation

The live preview doesn't regenerate the entire PDF on every change. Each proof gets its own fragment PDF, cached by SHA256 fingerprint. Only changed fragments regenerate. The fragments are then composed into a single preview PDF.

CoreText has two rendering paths

Default rendering uses CTFramesetter. When hyphenation is enabled, it switches to NSLayoutManager (TextKit). For strings over 2000 characters, unbounded layout is enabled to prevent CoreText truncation.

Arabic proofs auto-show based on charset

Arabic proof types appear in the sidebar only when at least one loaded font has Arabic characters in its charset. The check looks for a small set of core Arabic characters.

XcodeGen generates the project — don't edit .xcodeproj

The Xcode project is generated from TypeProofing-SwiftUI/project.yml. After adding or removing source files, run xcodegen generate. The pre-build script auto-builds Rust if libtpnative.a is missing.

Hanging punctuation uses AAT, not OpenType

Hanging punctuation is implemented via Apple Advanced Typography feature type 22 (optical bounds), not OpenType. Only fonts with the opbd table support it. FontLoader.fontSupportsOpbd() checks this.

WordSiv is charset-constrained

The WordSiv text generator produces words using only characters available in the loaded font. This means a font missing certain letters will still get readable text, just with a restricted vocabulary. Seed 987654 makes output deterministic.

"Generate Once" prevents duplicate rendering

The Custom Text proof with generateOnce: true renders the text exactly once using a specified default font, rather than once per loaded font. A static set tracks which instances have already generated within a session.
